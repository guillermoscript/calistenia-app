# apps/web: cardio, race, landing, blog, legal, infra

## Grade
**B-**. The landing/features/blog layer (`components/landing/*`, `featureShell.tsx`) is genuinely excellent — well-documented composition primitives, correct code-splitting, careful a11y and i18n discipline. The cardio/race tracking layer is functionally solid (good use of refs to dodge stale closures, careful cleanup effects, offline-safe queues) but has real duplication against `packages/core` (one file reimplements logic that already exists as a shared, tested pure function), two large god-functions for share-card canvas rendering, and two shipped debug/leftover artifacts visible to real users. Bundle/route splitting in `App.tsx` is correctly done (every secondary page is `lazy()`), but the file itself has accumulated triplicated nav config.

## Top 3 refactors
1. **Delete the reimplemented GPS-fix pipeline in `CardioSessionContext.tsx` (web) and call the shared `processCardioFix` from `packages/core/lib/cardio-fix.ts`** — mobile already does this; the web copy is a second, independently-maintained source of truth for distance/pace/gap/jitter rules that WILL drift (the core file's own comment admits it's "identical to mobile and web").
2. **Extract the two ~350–430 line `handleShare` canvas functions (`RaceShareCard.tsx`, `CardioShareCard.tsx`) into composed `draw*` helpers** (header/avatar, stat block, list, route, footer), building on the existing `canvas-helpers.ts` primitives instead of one giant imperative function per card.
3. **Remove the two shipped debug leftovers** (`RouteDrawer.tsx`'s always-visible `[v2] {debug}` panel, `CardioSessionPage.tsx`'s `build-v3` header tag) and fix the `(user as any)` casts by adding `referral_code`/`display_name` to the shared `User` type in `packages/core/types/index.ts`.

## Done well
- `components/landing/{shared,featureSections,panels,featureShell}.tsx` — genuinely strong composition-pattern work: explicit variant props (`cols?: 3 | 4`), children-based `Reveal`/`PhoneFrame` wrappers, and doc comments that explain *why* a constraint exists (e.g. why Tailwind classes must stay literal for purge, why `Reveal` must wrap a block element not a `<tr>`). This is the reference example the rest of the app should imitate.
- `App.tsx` route splitting: every secondary page is correctly `lazy()`-loaded (`CardioSessionPage`, `RacePage`, `RacesDiscoverPage`, `BlogPage`, `FeaturePage`, etc.), with `CardioSessionPage.tsx:79-86` proactively preloading the Leaflet/`RouteMap` chunk on `requestIdleCallback` so the map paints instantly on first use — a genuinely good perf pattern.
- `contexts/RaceContext.tsx` delegates cleanly to `lib/race/{raceApi,raceTracker,raceClock,raceSnapshot,raceRealtime}.ts` rather than inlining fetch/business logic — much better separation than the cardio context, despite similar complexity (server-time countdown, auto-finish races, retry-with-backoff push).
- `components/race/RaceLive.tsx` decomposes into small presentational subcomponents (`Stat`, `TargetBar`, `Leaderboard`) rather than one monolithic JSX return.
- `main.tsx` — well-reasoned stale-chunk-after-deploy recovery (`vite:preloadError` handler with a 10s anti-loop guard) and SW update flow with a non-intrusive toast; documented inline with the actual failure mode it addresses.
- `components/MarketingUnmask.tsx` — tiny file but the doc comment correctly flags the real risk (`unmaskTextSelector` resolves via `closest()`, so it unmasks the *entire* subtree — never wrap user content).
