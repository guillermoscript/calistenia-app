# Mobile: Social, Battles, Cardio & Races (apps/mobile/src)

## Grade
**B-.** The domain logic that matters most — battle scoring/ranking (`packages/core/lib/battle.ts`), reaction/comment mutations (`useReactions`/`useCommentReactions`), and the cardio GPS-fix pipeline (`packages/core/lib/cardio-fix.ts`) — is genuinely well-factored into `packages/core` with good docs and test coverage, and several components show deliberate, documented perf work (`RaceContext`'s memoized value, `BattleStandingsList`'s primitive-fed memo rows). But that discipline is inconsistently applied: three call sites read raw server `rank` instead of the tie-safe `battleDisplayRanks` the team already built for this exact bug class (#357), `CardioSessionContext.tsx` (683L) is a god provider that never got the same `useMemo` fix its sibling `RaceContext.tsx` already has, and there are three flavors of web/mobile duplication ranging from copy-pasted GPS filtering to byte-identical files that a known fix pattern (`raceClock.ts`) was never applied to.

## Top 3 refactors
1. **Fix the raw-`rank` bug across the battle UI.** `BattleStandingsList.tsx:189`, `BattleFinishedWaiting.tsx:61-65`, `battle-history.tsx` (via `useBattleHistory.ts:55`) all read `entry.rank`/`standing.rank` directly instead of `battleDisplayRanks()`, so tied players show as artificially ranked #2/#3 on the live board, the finished screen, and history — while `BattleResults.tsx` (which does use `battleDisplayRanks`) shows the same battle as tied. This is a live correctness bug in a shipped feature (#357), not a style nit.
2. **Split `CardioSessionContext.tsx` (683L) and `RaceContext.tsx` (535L) into composed hooks.** Each currently owns GPS tracking, PB persistence, live-notification/widget sync, crash-recovery snapshotting, and (for races) four independent "how does this race end" triggers, all in one provider. Extract `useGpsTracking`, `useCardioPersistence`/`useRaceAutoFinish`, and `useLiveNotification` so each has one reason to change. While in there, add the `useMemo` around `CardioSessionContext`'s `value` — `RaceContext` already has this fix, with a comment explaining the 2Hz-rerender cost it prevents; `CardioSessionContext` ticks `duration` every second with no memo, so every consumer (including `ActiveCardioBar`, mounted globally) re-renders every second.
3. **Collapse the web/mobile duplication cluster in cardio + races.** `apps/web/src/lib/race/{raceApi,raceRealtime,errors}.ts` are byte-identical to their mobile counterparts (confirmed via `diff`) and have zero platform dependency — move them into `packages/core/lib`, exactly the pattern the team already used for `raceClock.ts` (whose own comment documents this exact rationale). Separately, `apps/web/src/contexts/CardioSessionContext.tsx` reimplements the entire GPS-fix filtering pipeline inline instead of using `packages/core/lib/cardio-fix.ts`'s `processCardioFix`, which mobile already adopted — the constants have already started drifting in presentation.

## Findings

### High

1. **`apps/mobile/src/components/battle/BattleStandingsList.tsx:189`, `BattleFinishedWaiting.tsx:61-65`, `battle-history.tsx:72-74,100-107` (+ `packages/core/hooks/useBattleHistory.ts:55`)** — [Correctness-smell / DRY] Live scoreboard, finished-summary screen, and history all read the server's raw total-order `rank` instead of the tie-aware `battleDisplayRanks()` that `packages/core/lib/battle.ts` built specifically because "the server always breaks a dead heat with `tie_break_key`... reading its rank made one of two level people a loser" (per code comments referencing #357). `BattleResults.tsx` does it correctly via `battleResultView`. Evidence: `rank={entry.rank}` (BattleStandingsList.tsx:189); `rank: mine?.rank ?? null` (useBattleHistory.ts:55). Fix: derive rank via `battleDisplayRanks(standings)` at all three call sites.
2. **`apps/mobile/src/components/battle/BattleResults.tsx:78`, `BattleLobby.tsx:59,95`, `battle-create.tsx:133,139`** — [Separation-of-concerns / DRY] Battle preset name/description are hardcoded to `.name.es`/`.description.es` even though `packages/core/data/battle-presets.ts` defines `{ es, en }` and the *exercises* inside the same presets are correctly localized via `battleExerciseName(..., i18n.language)`. 3. **`apps/mobile/src/app/u/[id].tsx:98-160`** — [React-perf: async-parallel] Five independent `pb.collection()` fetches (`users`, `public_user_stats`, `public_prs`, `public_sessions`, `user_programs`), all keyed only on `userId`, are awaited sequentially rather than via `Promise.all`, turning the public profile screen into a 5-hop waterfall. 4. **`apps/mobile/src/app/u/[id].tsx:92-193`** — [Separation-of-concerns] The public profile screen builds its data (5 raw `pb.collection()` calls + month-calendar shaping) directly in a `useEffect` instead of a `packages/core` hook, unlike sibling screens that use `usePublicSessionDetail`/`useChallengeDetail`. Fix: extract `useUserProfile(userId)` into `packages/core/hooks`.
5. **`apps/mobile/src/components/social/CommentsSheet.tsx:363-403`** — [RN-perf: list-performance-callbacks/item-memo] `renderItem` builds fresh inline closures (`onReply`, `onDelete`, `onReport`) per row every render; `CommentBubble` isn't `memo`'d. Fix: pass stable per-id callbacks into a `memo`-wrapped `CommentBubble`.
6. **`apps/mobile/src/app/social.tsx:221-231`** — [RN-perf: list-performance-callbacks] Same pattern on the main feed: `FeedCard` gets fresh `onReact`/`onComment` closures per render and isn't memoized — this is the highest-traffic infinite-scroll list in the whole scope. 7. **`apps/mobile/src/contexts/CardioSessionContext.tsx` (683L)** — [SOLID-SRP] God provider: GPS fix processing (230-278), native live-notification/foreground-service driving (363,379,389,409,457), crash-recovery snapshot persistence (97-146,192-226,551-592), PB CRUD (407-547), widget-sync side effects (457,630,639), and an offline retry queue (125-146,594-648) all in one file. `finish()` alone (407-469) computes splits, writes to PB, syncs the widget, invalidates cache, and falls back to a retry queue. Fix: split into `useGpsTracking` / `useCardioPersistence` / `useCardioLiveNotification` composed by a slimmer provider.
8. **`apps/mobile/src/contexts/RaceContext.tsx` (535L)** — [SOLID-SRP] Same shape: realtime subscription lifecycle (210-259), GPS tracker + PB push loop with retry/backoff (266-374), analytics emission (152-164,380-466), crash-recovery snapshotting (318-324), and **four independent race-ending triggers** scattered across the file (all-done watchdog 124-130, `ends_at` watchdog 132-143, clock-tick deadline 166-204, GPS-tick target check 277-319) — each can independently call `apiFinishRace`. Fix: extract one `useRaceAutoFinish` hook owning every finish trigger, and `useRaceTrackerPush` for the GPS+push loop.
9. **`apps/mobile/src/contexts/CardioSessionContext.tsx:665-670`** — [React-perf: rerender-derived-state] The context `value` object is rebuilt every render with no `useMemo` — unlike `RaceContext.tsx:491-504`, which explicitly memoizes with a comment documenting this exact 2Hz-rerender problem. Since `duration` ticks every second while tracking, every consumer (`ActiveCardioBar`, mounted globally) re-renders every second. Fix: wrap the value object in `useMemo`, same as `RaceContext`.
10. **`apps/web/src/contexts/CardioSessionContext.tsx:275-373,199-243`** — [DRY] Web reimplements the entire GPS-fix filtering pipeline (accuracy threshold, jitter filter, gap detection, plausibility, split detection) inline instead of using `packages/core/lib/cardio-fix.ts`'s `processCardioFix`, which mobile already adopted. ## Done well
- `packages/core/lib/battle.ts` centralizes scoring, tie-breaking, and display-rank derivation (`compareBattleScores`, `battleScoresLevel`, `battleDisplayRanks`, `battleResultView`) with doc comments cross-referencing the issues that shaped each rule — genuinely a single source of truth, correctly consumed by `BattleResults.tsx`/`BattleScoreCell.tsx`.
- `BattleStandingsList.tsx`'s row component is `memo`'d and deliberately fed only primitives (not the raw `BattleStanding` object) so a per-second tick doesn't re-render every row — documented inline with the issue number that motivated it.
- `RaceContext.tsx:488-504` memoizes its context value with an explicit comment quantifying the re-render cost it avoids — exactly the fix `CardioSessionContext.tsx` is missing (finding #9).
- `packages/core/lib/cardio-fix.ts` is a clean, pure, tested extraction of the GPS-fix pipeline that mobile's context correctly calls into — the right shape, and the model web and `raceTracker.ts` should follow.
- `apps/mobile/src/lib/race/raceClock.ts` re-exporting `packages/core/lib/serverClock.ts` proves the team already recognizes and fixes the web/mobile byte-identical-copy problem — it just wasn't applied to `raceApi.ts`/`raceRealtime.ts`/`errors.ts`.
- `packages/core/hooks/useReactions.ts`/`useCommentReactions.ts` show careful optimistic-update design (onMutate snapshot + onError rollback) with comments documenting a previously-fixed toggle-inversion bug.
- `FeedCard.tsx` correctly uses `expo-image` with `cachePolicy`/`recyclingKey`/`transition`, and extracts `CardioMetrics` into its own component specifically to avoid inline-JSX allocation, with an explicit comment about why.
- `notifications.tsx` and `community-programs.tsx` route all data access through core hooks (`useNotifications`, `useCommunityPrograms`) with stable `keyExtractor` and `useCallback`-wrapped handlers.
- `BattleFinishedWaiting.tsx` gates its entrance animation behind `useReducedMotion()`.
- Consistent "best-effort, never throw" convention in `cardio-live.ts`/`sync-cardio-widget.ts` — auxiliary features degrade silently to Sentry rather than crashing an active GPS session.
