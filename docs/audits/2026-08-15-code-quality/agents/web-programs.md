# apps/web — Programs & Exercises (editor, detail, library, community)

Scope: pages/ProgramEditorPage.tsx, ProgramDetailPage.tsx, ProgramsPage.tsx, EditorPage.tsx, SharedProgramPage.tsx, CommunityProgramsPage.tsx, CommunityProgramDetailPage.tsx, ExerciseDetailPage.tsx, ExerciseLibraryPage.tsx; components/ExerciseCard.tsx, ExerciseCatalogPicker.tsx, ProgressionChain.tsx, ProgramSelectorModal.tsx, CommunityProgramHomeCard.tsx, WgerResultCard.tsx, YoutubeModal.tsx, MediaViewer.tsx; hooks/useExerciseCatalog.ts.

## Grade

**C+**. The community-programs subsystem (CommunityProgramsPage/CommunityProgramDetailPage/CommunityProgramHomeCard) is genuinely well built — logic lives in core hooks, components are decomposed, i18n is consistent. But the older program/exercise surfaces carry heavy, *already-diverged* duplication: three separate `inferCategory()` implementations, two separate `mapPBRecord()` implementations, three separate "fetch+shape program detail from PocketBase" implementations, and a confirmed rendering bug from skipping `localize()` on translatable fields. i18n coverage is inconsistent — some components are fully translated, others (ProgramSelectorModal, WgerResultCard, the public shared-program landing) are 100% hardcoded Spanish with no `t()` at all. ProgramEditorPage.tsx is a 933-line monolith when mobile already solved the same wizard with clean step components.

## Top 3 refactors

1. **Extract exercise-catalog domain logic to `packages/core/lib`.** `inferCategory()` exists 3x (ExerciseDetailPage, ExerciseLibraryPage, ExerciseCatalogPicker) with 3 different rule sets, and `mapPBRecord()` exists 2x (ExerciseDetailPage, ExerciseLibraryPage) with different field priorities. The same exercise is categorized/shaped differently depending on which page renders it — this is live drift, not theoretical duplication.
2. **Decompose ProgramEditorPage.tsx into step components**, mirroring `apps/mobile/src/components/program-editor/Step{Info,Phases,Days,Exercises}.tsx`, which mobile already extracted from what its own comment calls a "port of the web page." Web never did the equivalent split and is now the outlier at 933 lines vs. mobile's 240-line orchestrator + step files.
3. **Sweep the scope for missing/inconsistent i18n**, including a real bug: `SharedProgramPage.tsx`'s public landing skips `localize()` on translatable PocketBase fields that `ProgramDetailPage.tsx` correctly localizes, so a program with a non-string `name`/`description` (the `TranslatableField` object form) would render broken on the shared link page seen by logged-out visitors.

## Findings

### High

1. **God page / SRP violation, and drift vs. mobile's decomposition** — `apps/web/src/pages/ProgramEditorPage.tsx:59-933`. A single 933-line component renders all 4 wizard steps inline via `state.step === N` blocks (step 1: 237-320, step 2: 323-396, step 3: 399-588, step 4: 591-885). Mobile's equivalent (`apps/mobile/src/app/program-editor.tsx`, 240 lines) delegates to `StepInfo.tsx`, `StepPhases.tsx`, `StepDays.tsx`, `StepExercises.tsx` in `apps/mobile/src/components/program-editor/`. Category: SOLID-SRP / DRY (cross-platform). Fix: extract matching step components on web.

2. **`inferCategory()` triplicated and diverged** — `ExerciseDetailPage.tsx:81-108`, `ExerciseLibraryPage.tsx:99-148`, `ExerciseCatalogPicker.tsx:67-80`. Detail page and Library page share ~90% of the same keyword-matching logic but Library's version additionally checks `note.includes('lumbar')` and extra `movilidad`/`world` keywords that Detail's version lacks (`ExerciseLibraryPage.tsx:120-126` vs `ExerciseDetailPage.tsx:89-91`). CatalogPicker's version (`ExerciseCatalogPicker.tsx:67-80`) has a completely different signature (`muscles, name` vs `exercise, dayType`) and different rules (Spanish muscle-name keywords like `'pecho'`, `'tríceps'`). Same exercise → different category depending on the page. Category: DRY + Correctness-smell. Fix: one function in `packages/core/lib`.

3. **`mapPBRecord()` duplicated and diverged** — `ExerciseDetailPage.tsx:210-228` vs `ExerciseLibraryPage.tsx:252-269`. Detail's version: `note: rec.note ?? ''`, `description: rec.description || rec.note || ''`. Library's version: `note: rec.note || rec.description || ''` (priority swapped) and adds a `difficulty: rec.difficulty_level` field Detail's mapper omits entirely — meaning exercise difficulty silently disappears on the detail page. Category: DRY + Correctness-smell. Fix: one shared mapper in core.

4. **Program-detail fetch logic triplicated** — `ProgramDetailPage.tsx:153-311` (~150 lines) manually calls `pb.collection('program_phases'/'program_exercises'/'program_day_config').getList(...)` with the exact filter/sort (`filter, sort: 'sort_order'` / `'phase_number,sort_order'`) already implemented as a private helper `fetchProgramDetail()` in `packages/core/hooks/usePrograms.ts:219-233` — which isn't exported, so the page can't reuse it. `SharedProgramPage.tsx:89-118` implements a third, lighter variant of the same fetch for its preview. `apps/mobile/src/app/program/[id].tsx:105-112` implements a fourth variant (with a comment noting it must match `usePrograms.buildWeekDays`'s ordering by hand). Category: Separation-of-concerns + DRY. Fix: export and reuse `fetchProgramDetail` (or a purpose-built subset) from core in all call sites.

5. **Missing `localize()` — real rendering bug on the public shared-program page** — `SharedProgramPage.tsx:89-118`. `progRecord.name`/`progRecord.description` (lines 92-93) and `r.exercise_name`/`r.sets`/`r.reps`/`r.muscles` (lines 112-117) are assigned directly into UI state without `localize()`, even though these are `TranslatableField` (`Record<string,string> | string`, `packages/core/lib/i18n-db.ts:11`) — the same fields `ProgramDetailPage.tsx:169-170,250` correctly passes through `localize(x, locale)`. For any program whose name/description/exercise fields are stored as the object form, this un-authenticated, publicly-linked landing page (`SharedLanding`, seen by non-logged-in visitors following a share link) will render `[object Object]` instead of text. Category: Correctness-smell (High confidence, concrete repro path) + DRY (would have been avoided by finding #4).

6. **Pervasive i18n inconsistency — several components ship zero translation** despite the app having a full i18next setup used everywhere else in this scope:
   - `ProgramSelectorModal.tsx` — 0 `useTranslation`/`t()` calls; every string hardcoded Spanish (e.g. lines 51, 58, 61-65, 73, 81, 139, 149, 166).
   - `WgerResultCard.tsx` — 0 `t()` calls; hardcoded `'IMPORTAR'` (line 21), `'✓ IMPORTADO'`/`'IMPORTANDO...'`/`'IMPORTAR →'` (lines 51, 101).
   - `SharedProgramPage.tsx`'s `SharedLanding` (lines 153-250) — the public-facing landing for logged-out visitors is entirely hardcoded Spanish (`'Programa no encontrado'`, `'Volver'`, `'Programa compartido'`, `'REGISTRATE PARA USAR ESTE PROGRAMA'`, etc.) — the single most externally-visible page in scope has no i18n at all.
   - `ExerciseCatalogPicker.tsx` — `CATEGORIES` labels (lines 48-59, e.g. `'Todos'`, `'Movilidad'`) and `'AGREGAR'` (line 263), footer pluralization (line 315, hand-rolled `!== 1 ? 's' : ''` instead of i18next plurals) bypass `t()` even though the rest of the same file uses it.
   - Files that otherwise use `t()` still leak raw Spanish literals: `ProgramEditorPage.tsx` — `"FASES DEL PROGRAMA"` (326), `"AGREGAR FASE"` (333), `"ELIMINAR"` (350), `"EJERCICIOS"` (593), `"SIGUIENTE →"` (910), `"GUARDANDO..."`/`"GUARDAR"` (918), `"Paso X de 4"` (902); `ProgramDetailPage.tsx`'s `formatRelativeDate()` (lines 70-78) hardcodes `'hoy'`/`'ayer'`/`'hace N días'`; `ExerciseCard.tsx` line 132 `"✓ COMPLETADO"`, line 137 `"descanso {s}s"`.

   This is not caught by the recently-added i18n usage guard (project memory: PR #445, `usage.test.ts`), which only scans `t('…')` call sites — it can't see raw JSX text nodes. Category: correctness-smell / product-quality. Fix: sweep and move to locale keys; consider extending the guard to flag bare non-ASCII/Spanish text literals in JSX.

7. **State duplicated from a derivable prop — `setsLogged` never syncs with existing logs** — `ExerciseCard.tsx:51,86-111`. `const [setsLogged, setSetsLogged] = useState<number>(0)` starts at 0 and is only ever incremented by `handleQuickLog`/`handleFormLog`; it's never initialized or reconciled against the `logs` prop, which already carries today's logged sets (`recentLogs = logs.slice(0, 3)`, line 56). If the card remounts with pre-existing logs (switching days/tabs, returning to the workout screen), `setsLogged` resets to `0` and `isComplete` (line 55) goes out of sync with the real persisted state — the UI shows 0/N even though sets were already logged for that exercise. Category: React rerender-derived-state / Correctness-smell. Fix: derive initial count from `logs` (e.g. `useState(() => logs.length)` or compute `isComplete` from `logs.length + local increments` instead of a fully independent counter).

### Medium

8. **Missing phase-removal guard that mobile already has** — `ProgramEditorPage.tsx` has no effect clamping `selectedPhaseTab` after `removePhase` shrinks `state.phases`, unlike `apps/mobile/src/app/program-editor.tsx:55-57` (`useEffect(() => { if (selectedPhaseTab >= state.phases.length) setSelectedPhaseTab(...) }, ...)`, added with a comment "La fase seleccionada puede desaparecer al eliminar fases"). On web, removing a later phase while viewing an earlier `selectedPhaseTab` index beyond the new length leaves Steps 3/4 rendering no day/exercise data until the user manually reselects a tab. Category: Correctness-smell (cross-platform: mobile fixed a bug web still has).

9. **Extensive `as any` casts around cardio/circuit day fields** — `ProgramEditorPage.tsx` has 25 `as any` occurrences, e.g. lines 473, 476, 495, 505, 523-576, 657-670, all working around `EditorPhase`/day types in `useProgramEditor.ts` not modeling `cardioActivityType`, `circuitMode`, `circuitRounds`, `circuitWorkSeconds`, etc. Category: Spaghetti / `any` abuse. Fix: widen the day type in `packages/core/hooks/useProgramEditor.ts` (discriminated union on `type`) instead of casting at every call site.

10. **Duplicate share implementation** — `ProgramsPage.tsx:21-46` defines its own local `shareProgram()` (Web Share API + clipboard fallback), duplicating the already-existing, more capable `shareProgram()` in `apps/web/src/lib/share.ts` (built on a generic `shareContent()` with native/whatsapp/copy methods) that `ProgramDetailPage.tsx:17` correctly imports and uses. Category: DRY (same app, sibling files diverge). Fix: use `../lib/share`'s `shareProgram` in `ProgramsPage.tsx` too.

11. **Near-duplicate "search for tutorial" UI** — `MediaViewer.tsx:170-222` (YouTube tab) re-implements ~50 lines of markup that is nearly identical to `YoutubeModal.tsx:20-74` (same 3 actions: YouTube search link, Google search link, copy-to-clipboard, same icons/copy pattern). Both are wired up separately in `ExerciseCard.tsx:430-431` as alternate overflow-menu entries. Category: DRY. Fix: extract a shared `YoutubeSearchLinks` presentational component used by both.

12. **Repeated ad-hoc `exercises_catalog` fetching with no shared hook** — `ProgramDetailPage.tsx`, `SharedProgramPage.tsx`, `ExerciseCatalogPicker.tsx:126`, `ExerciseLibraryPage.tsx:397`, `ExerciseDetailPage.tsx:287` all call `pb.collection('exercises_catalog')...` directly with their own ad-hoc mapping, despite `hooks/useExerciseCatalog.ts` already existing for a related (name/muscles-only) use case. Category: Separation-of-concerns. Fix: consolidate into parameterized core hooks so pages stop reimplementing PB queries.

13. **Manual pagination window instead of virtualization for a ~1600-item list** — `ExerciseLibraryPage.tsx:476-483`. `PAGE_SIZE = 90`, `visibleCount` state resets via `useEffect` on every filter change; the code's own comment acknowledges "la catálogo es ~1600 entries and the grid is not virtualized." Category: React-perf (maps to `rendering-content-visibility`/list-virtualization guidance). Fix: use a virtualized list (react-window/react-virtual) instead of a hand-rolled slice-and-grow window.

### Low

14. **Giant useState cluster for mutually-exclusive display panels** — `ExerciseCard.tsx:35-52`, 13 separate `useState` calls including `showTimer`, `showYoutube`, `showMedia`, `showEditForm`, `showHistory`, `showProgression`, `showOverflow` — several are mutually exclusive "which panel is open" toggles that could collapse into one `activePanel` state or small reducer. Category: KISS.

15. **IIFE inside JSX for a pure computation** — `ExerciseCard.tsx:143-153` computes injury flags via an inline IIFE on every render instead of a `const` above the return. Category: KISS (low impact, small array).

16. **Unmemoized section-bucketing IIFE** — `ProgramEditorPage.tsx:682-883` wraps exercise-section grouping in `(() => {...})()` inside JSX, recomputed every render though derivable via `useMemo`. Category: KISS/React-perf (low impact, small arrays).

17. **`DAY_IDS`/day-order arrays duplicated across the codebase** — `ProgramEditorPage.tsx:57` (`DAY_IDS`), `apps/mobile/src/components/program-editor/constants.ts:48` (explicitly commented as a hand-kept "espejo" / mirror of the web file), and `ProgramDetailPage.tsx:68` (`DAY_ORDER`, same values) all redefine the same 7-day array independently, though `packages/core/types/index.ts:9` already exports a `DayId` union type with no matching array constant. Category: DRY (Low severity — static values, low change risk, but genuine duplication with a hand-synced comment admitting it).

## Done well

- **Community-programs subsystem** (`CommunityProgramsPage.tsx`, `CommunityProgramDetailPage.tsx`, `CommunityProgramHomeCard.tsx`) is a model for the rest of the scope: all business logic lives in core hooks (`useCommunityProgramDetail`, `useCommunityPrograms`, `useChallenges`, `getMilestoneState`), pages decompose into named sub-components (`ProgressSummary`, `MilestoneRow`, `MilestoneStateLabel`), state-dependent rendering uses an explicit `switch` (with a comment explaining why, over chained booleans), and i18n is complete and consistent.
- `ExerciseLibraryPage.tsx:430-441` explicitly documents and handles historical category-ID drift (`mobility`/`movilidad`, `skills`/`skill`) via a `CATEGORY_ALIASES` map with a comment — a good example of *deliberately* absorbing real-world data inconsistency instead of letting it silently break filtering.
- `ProgramDetailPage.tsx` makes consistent, correct use of `useMemo`/`useCallback` for derived values (`phaseWorkouts`, `totalExerciseCount`, `difficulty`, `workoutDurations`) despite being a large file.
- `ProgressionChain.tsx` and `EditorPage.tsx` are small, focused, fully typed, fully translated, and free of smells — good examples of presentational components done right.
- The click-outside-to-close pattern for overflow/context menus (`ExerciseCard.tsx:69-76`, `ProgramsPage.tsx:77-86`) is implemented consistently and correctly with proper cleanup.
